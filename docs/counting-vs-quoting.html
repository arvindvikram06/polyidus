Reviewer bot · experiment result

Counting vs Quoting

Two ways to decide which line a comment belongs on. We ran both on the same pull request. One posted more comments. The other posted no wrong ones.

Everything here comes down to one small question.

The bot finds a problem. To leave a comment on the line, it has to tell GitHub a number: "put this on line 75."

Where does that number come from? There are only two ways to get it, and that choice is the entire argument.

WAY 1

Counting — what Oswald does

the model does arithmetic in its head

The model is shown the diff. A diff starts with a header like @@ -0,0 +1,98 @@, which means "in the new file, this chunk starts at line 1".

From there the model must count every single line break to reach the problem. Blank lines count. Every line of a long string counts. Miss one and every number after it is wrong.

Then it reports a number, and that number is used. Nothing checks it.

WAY 2

Quoting — what this project does

the model copies, the code searches

The model is not asked for a number. It is asked to copy the bad line, exactly as written.

Then our code opens the real file and searches for that text. Wherever it appears, that is the line. No arithmetic, no guessing.

The idea behind it is simple: copying is easy, counting is hard. Models are good at copying and bad at counting.

One finding, both ways

the clearest single comparison we have

Both modes found the same problem: "SaveChangesAsync is being called inside a loop." Same pull request, same file.

Here is the actual code, and where each mode put its comment.

The worst one

The finding "Credentials logged in plaintext" was posted on lines 40–42:

var created = 0;   var updated = 0;   var failed = 0;

Three counters. The code that actually leaks the password is at lines 36–38. So the comment accuses three harmless lines of logging secrets, and the real offender has no comment on it at all.

THE TRAP

Why 10 looks better than 6

and why it isn't

Your instinct was reasonable. Ten tidy inline comments look like a better review than six with three of them dumped at the top of the file. Anyone would think that.

Here is the thing that flips it.

The point of a line comment

The only reason to attach a comment to a line is so the reader does not have to hunt for the problem. That is the entire value.

If three in ten point at the wrong place — and you cannot tell which three — then you have to verify all ten by hand. The comments have stopped saving you anything. They now cost you time.

Think of a proofreader. One hands back your essay with ten red circles, three of them around perfectly good sentences, and won't say which. The other circles six, and writes "something's off in this paragraph, I can't pin it down" three times.

The second one is more work to look at. It is also the only one you can trust.

NEXT

What to do about it

quote mode has two real gaps — both fixable

Quote mode is not perfect. Six of ten findings failed to get a line, for two specific reasons. Both are small and fixable, and neither requires giving up the verification.

Gap 1 — the model quoted something too short

the model copied:  "catch"
the problem:       that word appears all over the file.
                   Searching for it finds eight places. Which one?
so we refused — and the comment fell to file level.

the fix: tell the model that if the line is short or repeated,
          quote two or three lines together. Our search already
          handles multi-line quotes.

Gap 2 — the model changed the quotes while copying

the file says:     ... SupplierCode = '" + supplierCode + "' ...
the model wrote:   ... SupplierCode = '" + supplierCode + “' ...
                                                     ↑ curly quote

so the search found nothing — the text does not match.

the fix: treat curly quotes as straight quotes before matching.
          A few characters of code.

Fix those two and most of the six become real line comments. Still verified. Still zero wrong.

The flag for Oswald mode is left in the code — REVIEWER_TRUST_MODEL_LINE_NUMBERS=1 — so this can be re-run any time. It is off by default, and it warns loudly whenever it is on.
