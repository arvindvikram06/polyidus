Reviewer bot · architecture · revised plan

Threads as State

Stop building a database that mirrors the pull request. Put every finding on the line it is about, and let GitHub hold the record — seven tables become two.

We spent a week designing tables to remember what the bot said, which findings a human overruled, and how to address one finding out of six. GitHub already stores all of that.

Not as a convenience — as its actual data model. A comment on a line of code is not a message. It is a thread, and a thread is a row with a user interface attached.

PART 1

What a thread actually is

the word doing all the work in this plan

In plain terms

On GitHub, when you comment on a specific line of code in the Files changed tab, you don't post a message. You open a thread.

A thread is a little conversation pinned to that line. Other people reply inside it — their replies belong to that thread, not to the pull request in general. And it has a Resolve conversation button. Click it and the thread collapses and is marked resolved.

That's the whole trick. A thread already has everything we were going to build:

  • an id — so you can address one finding out of six
  • a file and line — so nobody has to ask "which one?"
  • an ordered list of replies — the argument, preserved
  • a resolved flag — the decision, stored by GitHub

That is a database row. GitHub stores it, renders it, notifies people about it, and lets humans edit it — none of which our table would have done.

Technically

Threads are created by POST /pulls/{n}/reviews with a comments[] array — one request, one notification, however many comments. Replies go to POST /pulls/{n}/comments/{id}/replies. Reading back is GET /pulls/{n}/comments, where every reply carries an in_reply_to_id pointing at its thread root.

One wrinkle worth knowing before we build: the resolved flag is not in the REST API. Review-comment objects don't carry it. It lives on GraphQL's PullRequestReviewThread.isResolved, and resolving is the resolveReviewThread mutation. So "has this been dealt with?" needs one GraphQL query alongside the REST calls. The webhook side is fine — pull_request_review_thread fires with resolved / unresolved actions.

PART 3

Inline comments, without wrong lines

the thing that makes all of the above safe

Why this is the hard part

Everything above depends on the comment landing on the right line. Get it wrong and the bot posts a confident remark about code that has nothing to do with it — which is how a reviewer stops being trusted.

And GitHub will only catch some of it. It rejects a line outside the diff entirely. A wrong line that happens to be inside the diff posts silently.

This is Oswald's weakest point

Its code-reviewer skill tells the model to do the arithmetic by hand:

"Parse the diff header to determine the starting line number. Count EVERY physical line break from that start index. CRITICAL: count lines inside multi-line strings individually — failure to do this causes 'Off-by-N' errors."

Read the tone. The all-caps, the named bug, the follow-up "mental check" step — that is prompt text that grew out of hitting the problem repeatedly. It is the same approach we started with, and measured: off by 1 to 14 lines, with two findings in a single review reporting 17-18 and 11-12 for the same pair of constants that actually sit at 16-17.

The fix was to stop asking the model to count. It is asked to copy — quote the offending line verbatim — and we do the searching. Copying is something models do reliably; arithmetic through a hunk header is not.

That took anchoring accuracy from 1 out of 5 correct to 6 out of 6.

The three failure modes, and where each is handled

Quote not in the file. The specialist named the wrong file, or invented the line. locate() returns nothing rather than a guess, and the finding drops to file level. A comment on the right file is recoverable; a confident comment on unrelated code is not.

Quote appears several times. A repeated assignment, a common brace. Prefer a line the pull request actually added, then fall back to the model's own number as a tie-breaker — its absolute counting is untrustworthy, but as a hint about which of several identical lines it meant, it is fine.

The head moved mid-review. Someone pushed between the review starting and the comments posting, so every line has shifted. The review is pinned to commit_id, so GitHub rejects it rather than attaching comments to moved code.
